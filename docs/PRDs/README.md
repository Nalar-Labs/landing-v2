# PRDs

A **PRD** is the high-level requirements document for a piece of work: what we're
building and why, the decisions and their trade-offs, and the risks. It is
written and agreed *before* implementation starts.

Every PRD lives in this folder. There is no other home for them.

## PRD → superpowers plan

A PRD is **not** an implementation plan. The two are separate artifacts and the
order matters:

| | PRD | Superpowers plan |
|---|---|---|
| Answers | *what* and *why* | *how* |
| Location | `docs/PRDs/` | `docs/superpowers/plans/` |
| Author | written and agreed with Garda | generated by the superpowers skill |
| Naming | this convention (see below) | the skill's own — **leave it alone** |

The flow is **PRD first, then superpowers.** Agree the requirements and the
trade-offs, then hand the PRD to the superpowers skill to produce the detailed
implementation plan, then execute that.

Superpowers plans are kept as a record of how something was actually built.
**Do not move, rename, or fold them into this folder** — they are a different
artifact with a different lifecycle.

## Naming

```
YYYY-MM-DD_<slug>_<STATUS>.md
```

- **`YYYY-MM-DD`** — the date the document was **last updated**, not the date it
  was created. Rename the file when you meaningfully revise it. Date-first keeps
  the folder sorted chronologically.
- **`<slug>`** — short, kebab-case, names the feature (`portfolio-video`).
- **`<STATUS>`** — uppercase, one of:

| Status | Meaning |
|---|---|
| `PENDING` | Agreed or in progress, not yet live. |
| `DEPLOYED` | Shipped to production. |
| `ICEBOXED` | Deliberately parked. Keep the file — the reasoning is the value. |

Example: `2026-08-09_portfolio-video_PENDING.md`

**Status changes are renames.** A PRD moving from `PENDING` to `DEPLOYED` is
`git mv` plus a date bump, so the filename never disagrees with reality.

> Written without `[` `]` around the status on purpose: square brackets are glob
> metacharacters in bash and zsh, so `ls *[Pending]*` misbehaves and every path
> needs quoting. Underscores keep the files easy to work with on the command line.

## Writing one

State the decisions and their trade-offs, not just the conclusion — the reason a
path was rejected is usually the most valuable thing in the document six months
later. Include the risks and how each is mitigated, and be explicit about what
is *not* covered (for example, which steps have no automated test path).

Keep a `Status:` line at the top of the document as well, so the state is visible
when the file is open and not only in its name.
