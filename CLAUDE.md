# Nalar Labs — landing-v2

Marketing landing page for Nalar Labs. Vite + React 18 + TypeScript + Tailwind v4,
with shadcn/ui primitives. Repo: `Nalar-Labs/landing-v2`.

## Workflow — PRD → superpowers plan → build

Any non-trivial feature follows this order. The two documents are **separate
artifacts**; do not merge them or move one into the other's folder.

**1. PRD** — the high-level requirements: *what* and *why*, decisions with their
trade-offs, risks. Written and agreed before code. Lives in `docs/PRDs/`.
Full convention: [`docs/PRDs/README.md`](docs/PRDs/README.md).

- Filename: `YYYY-MM-DD_<slug>_<STATUS>.md`, date = **last updated**,
  status = `PENDING` | `DEVELOPED` | `DEPLOYED` | `ICEBOXED`.
  `DEVELOPED` means built and merged but **not live** — "built" and "shipped" are
  different states here, so don't collapse them.
- Status changes and revisions are **renames** (`git mv`), so the filename never
  disagrees with reality. Keep the `Status:` line inside the doc in sync.
- Keep rejected options and the reasoning — that's the value six months later.

**2. Superpowers plan** — the *how*, generated by the superpowers skill from the
agreed PRD. Lives in `docs/superpowers/plans/` with the skill's own naming.
**Leave these files alone** — don't rename them, don't move them into `docs/PRDs/`.
They are the record of how something was actually built.

**3. Build** against the superpowers plan.

## Commands

```bash
npm run dev     # Vite dev server on :5173
npm run build   # production build
```

There is no `npm test` script. Tests are pure-logic Node tests, run per file:

```bash
node --test --experimental-strip-types src/app/data/portfolio.test.ts
```

There is **no jsdom / RTL / vitest** — component and interaction behaviour is
verified manually in the browser, not by automated tests. Don't claim component
coverage that doesn't exist.

## Architecture

- `src/app/sections/` — page sections (`Hero`, `Services`, `Portfolio`, …)
- `src/app/components/` — reusable pieces; `components/ui/` is shadcn, keep as-is
- `src/app/data/` — content + pure parsing logic (must run under `node --test`,
  so **no Vite APIs** here; `import.meta.glob` loaders go in `*-items.ts`)
- `src/app/lib/` — hooks and helpers, incl. `layout.ts` (`cn`, `TYPE`, `SECTION`)
- `src/content/portfolio/*.json` — CMS-authored portfolio items

## Design system

Tokens live in `src/styles/theme.css` and are documented in
[`guidelines/Guidelines.md`](guidelines/Guidelines.md). Use the semantic
utilities — `bg-brand`, `text-muted-ink`, `border-line`, `rounded-card`,
`font-display` — and the `TYPE` / `SECTION` constants from `lib/layout.ts`.
**Never hard-code hex values, font names, or ad-hoc pixel spacing** in a
component. Black-on-white, Public Sans, one orange accent (`#ff5900`) for the
single primary action per view. No drop shadows.

## Content / CMS

Portfolio items are JSON edited through Sveltia CMS — see [`docs/cms.md`](docs/cms.md).
It is **git-based**: `media_folder` commits uploads straight into the repo, so
never route large binaries (video) through it. `parsePortfolioItems` throws on
invalid content on purpose, so a bad file fails the build instead of silently
dropping an item from the site.

## Gotchas

- **Lenis owns wheel events site-wide.** Any independently scrollable area needs
  `data-lenis-prevent` (see `PortfolioModal`).
- **Radix keeps dialogs mounted ~200 ms after close.** Don't rely on unmount to
  stop media or clear state — do it explicitly.
